# MVU 風格動態變量卡設計指南

「MVU」在酒館社群裡泛指讓角色卡具備**跨對話持久記憶的數值狀態**（好感度、關係階段、心理值……），並且讓這些狀態能被模型讀取、更新，甚至視覺化呈現。有些使用者的 SillyTavern 裝了專門的變量擴充套件，語法會不同；但即使沒有裝任何擴充，也可以用「世界書條目 + JSON Patch 慣例 + regex 隱藏/美化」這套**不依賴額外擴充、純用卡片本身機制**的做法達到一樣的效果——這是本技能預設採用的方式，因為它最容易被任何人的酒館環境正確運行，也方便日後除錯。

## Step 1：先決定要不要做

不是每張卡都需要。判斷依據：

- 這個角色的行為/語氣會不會隨「好感度」「信任度」這類看不見的數值明顯分階段變化？→ 需要
- 使用者會不會想要在介面上一眼看到目前進度（例如好感度條、關係標籤）？→ 需要
- 卡片主要是日常向、單元劇形式，每次互動相對獨立，沒有強烈的「養成」需求？→ 通常不需要，硬做反而增加維護負擔與 token 成本

如果不確定，直接問使用者：「你會希望這個角色的態度隨好感度變化，而且變化過程要有數值可以追蹤嗎？」

## Step 2：設計 STATUS_DATA 的欄位

跟使用者一起列出要追蹤的變量，每個變量標明型別與範圍：

| 變量類型 | 範例 | 說明 |
|---|---|---|
| 核心數值（0-100） | 好感度、信任值、警戒心 | 決定關係階段轉換的主要數值 |
| 輔助數值（0-100） | 心跳失控、黏人指數 | 用來反映當下情緒波動，可能比核心數值更頻繁變動 |
| 階段標籤（文字） | 關係階段、Phase標籤 | 依核心數值門檻動態生成，用一段話而非只是「Phase 1」這種內部代號，方便直接顯示給使用者看 |
| 場景記憶（物件） | 筆記本 { 玩家穿著, 兩人姿勢, 當前場景速寫 } | 讓模型記住一些「這一頁還在講什麼」的細節，避免下一輪失憶 |
| 計數器 | page（第幾輪/第幾頁） | 用來做冷卻機制或里程碑判定 |

把這份設計寫成一個 JSON 範例，放進一條 `constant: true` 的世界書條目（`comment` 建議取類似 `01_Data_Char_Vars` 這種易辨識的名字），當作「初始值/欄位定義」的說明文件。**這條通常設 `enabled: false`**（它是給人看的欄位字典，不是每輪都要注入的內容；真正的初始值建議直接寫進 `first_mes` 開頭或另一條常駐條目）。

```json
[STATUS_DATA]
{
  "好感度": 5,
  "心跳失控": 15,
  "關係階段": "初次相遇",
  "Phase標籤": "🧱 保持距離",
  "page": 1,
  "筆記本": {
    "玩家穿著": "未記錄",
    "兩人姿勢": "未記錄",
    "當前場景速寫": "未紀錄"
  }
}
```

## Step 3：設計「變量更新腦」條目

這是另一條 `constant: true` 的世界書條目，內容是**寫給模型看的操作指令**，不是敘事文字。核心要求：

1. 每輪正文結束後，必須換行輸出一段變量異動記錄。
2. **嚴禁在旁白/對話裡直接提到具體數值或內部欄位名稱**——數值只活在這段結構化記錄裡，故事裡只能透過行為間接呈現（例如好感度上升不能寫「好感度+10」，只能寫角色的具體反應變化）。
3. 用 [JSON Patch（RFC 6902）](https://datatracker.ietf.org/doc/html/rfc6902) 的 `{ "op": "replace", "path": "/欄位", "value": 新值 }` 格式描述每個異動的欄位，並且把整段記錄包在 HTML 註解裡，這樣它不會被玩家直接看到原始文字，之後也方便用 regex 完全隱藏或轉換成別的呈現方式：

```
<!-- <VariableUpdateLog><JSONPatch>
[
  { "op": "replace", "path": "/好感度", "value": NEW_VALUE },
  { "op": "replace", "path": "/關係階段", "value": "NEW_STAGE" },
  { "op": "replace", "path": "/page", "value": CURRENT_PAGE_PLUS_1 }
]
</JSONPatch></VariableUpdateLog> -->
```

4. 如果有階段標籤這種「依數值門檻動態生成文字」的欄位，把門檻規則寫清楚，例如：

```
若 好感度 < 40：Phase標籤 需濃縮當前「保持距離」的情境
若 好感度 40~79：Phase標籤 需濃縮當前「動搖試探」的情境
若 好感度 ≥ 80：Phase標籤 需濃縮當前「卸下防備」的情境
```

## Step 4：讓變量真正「動起來」而不是裝飾

寫完變量系統後,務必回頭檢查 `system_prompt`／角色設定裡的行為描述，是否真的隨這些階段門檻分層寫清楚差異（表象 vs. 內心、行動模式的具體差異），否則就算數值有在更新，角色的實際演出也不會跟著變——變量系統只是記錄工具，真正驅動變化的仍然是你在 Stage 2 checklist 裡確認過的「心理狀態進展脈絡」。

## Step 5：交給 Stage 5 做視覺化

STATUS_DATA 本身只是資料，怎麼呈現給使用者看是 Stage 5（regex 美化）的責任——通常會另外設計一條 `[HEADER_CARD]`/`[FOOTER_CARD]` 這類純文字標記的輸出格式指令條目，模型把當前變量值填進標記裡，再靠 regex 轉成好感度條、狀態徽章等視覺化 HTML。細節見 `regex-beautify-guide.md`。

## 如果使用者的酒館裝了專門的變量擴充套件

有些使用者環境裡裝了社群開發的「變量卡」/MVU 擴充（語法可能是 `_.變量名 = 值` 或專屬的 `<UpdateVariable>` 區塊，依擴充版本而異）。如果使用者明確說明自己有裝這類擴充並想用它的語法，就照使用者提供的語法規範走，不要硬套本文件的 JSON Patch 慣例；但如果使用者不確定或沒有特別指定，優先採用本文件「世界書 + JSON Patch + regex」的做法，因為它不需要額外安裝任何東西就能運作，可攜性最好。
