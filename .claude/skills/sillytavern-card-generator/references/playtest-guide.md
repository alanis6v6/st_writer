# 試玩模擬（Playtest Dry-Run）指南

## 目的與定位

這個功能不是要「演到全劇終」，而是要讓使用者看到：**用一個普通玩家的節奏玩下去，這張卡實際上會長成什麼樣子**——世界書會不會在該觸發的時候觸發、好感度之類的數值推進得順不順、regex 卡片渲不渲染得出來、Phase 轉換有沒有卡住或跳級、文風有沒有跑掉。這是**品質檢驗**，不是展示作。所以模擬過程中發現的問題（觸發不到的世界書條目、變量卡死、節奏太快太慢）都要老實記錄下來，不要為了讓成果好看而暗中修正。

**準確性的關鍵原則**：能算清楚的東西一律用 `scripts/playtest_engine.py` 算，不要靠自己「感覺」世界書有沒有觸發、變量有沒有更新對——那樣得到的只是「我覺得這張卡會怎麼跑」，不是「這張卡真的會怎麼跑」。腳本負責世界書關鍵詞掃描、regex 美化渲染、JSON Patch 變量更新這三件可以精確計算的事；你負責的是**玩家會怎麼反應、角色會怎麼演**這種需要判斷力和創作力的部分。兩者分工，模擬結果才站得住腳。

## 觸發時機

卡片組裝完成（Stage 7）之後，使用者要求「試玩」「模擬跑一輪」「看實際效果」「跑 20 頁看看」之類的請求時，進入這個階段。

## Step 1：跟使用者確認模擬參數

不用問到鉅細靡遺，抓幾個關鍵決策就好：

- **輪數/頁數**：預設 20 頁（一頁＝玩家一輪＋角色一輪），使用者可以調整。
- **玩家人設**：預設用「好奇但穩健推進」的一般玩家——會主動探索、偶爾試探親密邊界，但不會一開場就衝極端；每輪 1-2 句動作描述＋1-2 句對話，貼近真人玩家會打字的長度和口氣（不是華麗的旁白文筆，是一般人邊玩邊打字的樣子）。如果使用者想模擬特定類型的玩家（被動觀察型、直球型、話多型），照使用者說的調整。
- **起手情境**：用哪一個開局（`first_mes` 還是某個 `alternate_greetings`）？如果卡片有多開局，問使用者要測哪一個，或分別各跑幾輪。

## Step 2：初始化

```bash
mkdir -p playtest_run
cp <組好的角色卡>.json playtest_run/card.json
```

`state.json`、`transcript.json`、`transcript.html` 會由腳本自動建立在你指定的路徑，不用手動建立空檔案。

## Step 3：逐輪執行（對每一頁重複）

這是核心迴圈，每一頁重複一次：

1. **取得這一輪該用的上下文**（角色轉頭寫之前一定要先跑這步，不要跳過）：

   ```bash
   python3 scripts/playtest_engine.py context \
     --card playtest_run/card.json \
     --state playtest_run/state.json \
     --transcript playtest_run/transcript.json \
     --round <N>
   ```

   這會印出「這一輪真的會被注入的世界書內容」＋「目前的變量狀態」。**只用這份輸出裡列出的世界書內容，不要偷用你自己記得的、但這一輪其實沒被觸發的設定**——這正是模擬的意義所在：如果某個你以為理所當然會知道的細節，這一輪其實沒被關鍵詞觸發，角色的演出就應該表現出「不知道/沒被提起」，這種落差本身就是很有價值的 QA 發現，記下來。

2. **寫玩家這一輪的台詞**（存成一個 txt 檔，例如 `playtest_run/p<N>.txt`）：1-2 句動作＋1-2 句對話，語氣像真人玩家在打字，不是小說旁白。要讓玩家有推進感——嘗試不同的互動方式（有時候問問題、有時候做動作、偶爾試探角色的邊界），不要每一輪都用同一種句型，否則測不出角色在不同刺激下的反應差異。

3. **依卡片的 `system_prompt` 規則，完整寫出角色這一輪的原始輸出**（存成 `playtest_run/c<N>.txt`）：包含卡片規定的所有結構——字數限制、`[HEADER_CARD]`/`[FOOTER_CARD]` 這類純文字標記、`<!-- <VariableUpdateLog>... -->` 變量更新區塊——一字不漏照卡片的格式規定寫，因為這份原始文字接下來要被腳本實際解析、實際套用 regex，任何格式不合規都會在下一步顯形（這也是重要的 QA 訊號：如果你發現自己很難穩定按照卡片規定的格式輸出，那通常代表這張卡的格式指令寫得不夠清楚，值得回頭修）。

4. **提交這一輪，讓腳本套用規則並更新紀錄**：

   ```bash
   python3 scripts/playtest_engine.py commit \
     --card playtest_run/card.json \
     --state playtest_run/state.json \
     --transcript playtest_run/transcript.json \
     --round <N> \
     --player-file playtest_run/p<N>.txt \
     --char-file playtest_run/c<N>.txt \
     --html playtest_run/transcript.html
   ```

   腳本會回報：JSON Patch 有沒有成功解析（`patch_found`）、套用後的變量值（`vars_after`）、regex 渲染時有沒有警告（`warnings`，例如某條 regex 編譯失敗、抓不到匹配）。**這些警告要老實記下來**，最後的 QA 摘要要提到。

5. 重複 1-4，直到跑完使用者要的輪數。

## Step 4：交付與 QA 摘要

跑完全部輪數後：

1. 用 Artifact 工具把 `transcript.html` 發布出去（發布前先照一般流程載入 `artifact-design` skill 走一次設計檢查，畢竟這是要給使用者看的成品，不是暫存檔）,或至少用 SendUserFile 把檔案交給使用者，讓使用者能實際捲動看完整份模擬對話與規則渲染後的樣子。
2. 附上一段簡短的 QA 觀察摘要，具體點出：
   - **變量推進節奏**：好感度之類的數值有沒有隨互動自然爬升？有沒有卡住不動、或衝太快跳過中間階段？
   - **世界書觸發狀況**：哪些條目整場都沒被觸發過（可能關鍵詞設太窄，或這場模擬剛好沒聊到）？有沒有意外頻繁觸發、可能會擠壓上下文的條目？
   - **regex 渲染狀況**：有沒有出現 `warnings`？渲染出來的卡片版面在瀏覽器裡看起來正常嗎？
   - **Phase/心理狀態轉換**：如果卡片設計了階段狀態機，轉換時機看起來合理嗎，還是感覺被觸發得太早/太晚？
   - **文風一致性**：20 頁下來語氣、稱呼、口頭禪有沒有飄掉？
3. 問使用者：根據這些觀察，要不要回頭調整世界書關鍵詞、regex、變量門檻，或敘事規則？——試玩的價值就在於把這些問題攤開來一起改，不是模擬完就結束。

## 常見陷阱

- **不要幫角色作弊**：如果這一輪 `context` 沒印出某個世界書條目，角色的演出就不該表現得好像知道那件事。
- **不要為了讓變量曲線好看就手動調整輸出的 JSON Patch 數值**——照角色在這一輪的實際反應誠實地給分，跑出來不夠自然的曲線本身就是要回報給使用者的發現。
- **玩家輪不要寫得像小說**——如果玩家台詞寫得跟角色的文學腔一樣華麗，測不出角色卡在面對「普通人講話方式」時的真實反應，會失去測試的意義。
- **不要在中途發現問題就默默在腦內修正卡片邏輯後繼續跑**——先把 20 頁跑完、如實記錄問題，修正留到 Step 4 使用者確認要調整之後再進行，避免測試樣本一半用舊邏輯、一半用新邏輯，結果無法解讀。
