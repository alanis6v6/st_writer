# 世界書（World Info / Lorebook）設計指南

世界書不是「把設定寫成一堆條目塞進去」，而是一套**觸發系統**：每條條目都要回答「什麼情況下該被想起來」，而不是「這個角色的所有事情」。塞太多常駐條目會擠爆上下文、稀釋角色扮演的專注度；關鍵詞設得太窄會導致該觸發時沒觸發，設太寬又會誤觸發。這份指南幫你跟使用者一起把每條世界書設計清楚。

## 每條世界書條目要決定的事

依照 Stage 2 checklist 整理出的登場人物/世界觀規則/事件/NPC，逐一設計以下欄位（欄位名稱對齊 SillyTavern V3 `character_book.entries[]` 的實際 schema，精確型別見 `card-format.md`）：

| 欄位 | 設計問題 |
|---|---|
| `keys`（主要關鍵詞） | 這條內容應該在對話出現哪些詞的時候被想起來？通常放：角色姓名、暱稱、稱謂、代表性物品、地點名。關鍵詞太少會漏觸發，建議至少 3-5 個同義變體（本名、暱稱、關係稱謂）。 |
| `secondary_keys`（次要關鍵詞） | 需不需要「兩個條件同時滿足才觸發」？例如「地點=辦公室」+「事件=加班」才觸發某段細節。搭配 `selective: true` 與 `selectiveLogic`（AND_ANY / AND_ALL / NOT_ANY / NOT_ALL）使用。 |
| `constant`（是否常駐） | 這條內容是「每一輪都該在」（例如世界觀氛圍、語言風格規範、變量更新指令），還是「符合條件才該在」（例如某個 NPC 的介紹）？常駐條目要精簡，因為每輪都會佔用上下文。 |
| `position` / `extensions.depth` | 插入位置——放在角色設定之前還是之後？如果要模擬「這是最近幾輪對話才該想起來的事」，用 at-depth 插入並調整深度。深度數字愈小，代表愈接近對話最新的位置，對模型的即時影響力愈強。 |
| `insertion_order` | 多條同時觸發時的插入順序，數字愈小通常代表愈優先/愈晚被截斷保留。彼此有依賴關係的條目（例如先講規則、後講細節）要留意順序。 |
| `extensions.probability` / `useProbability` | 要不要做成「符合關鍵詞也不是每次都觸發」的機率事件？搭配 Stage 2「特殊事件」裡的隨機事件設計。 |
| `extensions.group` / `group_override` / `group_weight` | 多個條目互斥時用分組（例如「今天的隨機小插曲」有 5 種、每次只能觸發 1 種）。 |
| `extensions.sticky` / `cooldown` / `delay` | 觸發後要不要「黏著」幾輪不消失（sticky）？觸發後要不要「冷卻」幾輪不能再觸發（cooldown，很適合用在 Stage 5 的小遊戲/事件冷卻機制）？要不要「延遲」到對話進行幾輪之後才可能觸發（delay，避免劇情一開場就被事件洗版）？ |
| `use_regex` | 關鍵詞是否要當正規表達式解讀（進階用法，多數情況維持純文字關鍵詞即可）。 |

## 常見的世界書條目分類（對應 checklist 的七個面向）

1. **世界觀氛圍**：`constant: true`，內容精簡（時代/地點/感官基調），因為每輪都會注入。
2. **NPC 介紹**（每個 NPC 一條）：`selective`，關鍵詞用 NPC 姓名/暱稱/身分稱謂，內容包含性格、與主角關係、在場時會怎麼影響主角行為。
3. **地點介紹**（住所、工作場所等常回訪的場景）：`selective`，關鍵詞用地點名稱，內容可包含空間細節、常駐物品（能被角色無意識互動的道具，例如筆記本、寵物）。
4. **隨機/特殊事件**：`selective` + `useProbability`，機率值依事件稀有度設定（10-30% 常見）。
5. **過去經歷／深層設定**：`selective`，關鍵詞設定得narrow一點（例如只在使用者主動追問時觸發），並在條目內容裡標註「這是需要玩家透過互動解鎖的層次，不要主動在旁白劇透」，或搭配 `system_prompt` 的反劇透原則。
6. **情感/親密偏好**：`selective`，避免設為 constant——這類內容通常涉及親密情境，只在情境接近時才需要注入，平常留在背景不佔上下文。
7. **系統性條目（變量/顯示格式指令）**：如果有做 MVU（見 `variable-system.md`），通常會有 2-3 條 `constant: true` 的系統條目，分別放「當前變量快照」「變量更新規則」「輸出格式指令」，這些是說給模型聽的操作手冊,不是說給讀者聽的敘事內容。

## 跟使用者確認時的檢查問句

- 「這個關鍵詞會不會太常見，導致平常聊天也誤觸發？」（例如用「他」「這裡」當關鍵詞幾乎必然誤觸發）
- 「這條內容需要每一輪都在嗎，還是符合情境才需要？」
- 「有沒有兩條世界書內容其實互斥，應該分組讓只有一條生效？」
- 「這個 NPC / 事件會不會在使用者還沒探索到的階段就被劇透？」——需要的話用 `delay` 或提高關鍵詞門檻。

## 範例：一條完整的 NPC 世界書條目（概念示意）

```
keys: ["阿宇", "李昕宇", "咖啡廳老闆"]
secondary_keys: []
comment: "阿宇（好友NPC）"
content: "李昕宇（阿宇），主角的大學同學，在海邊開咖啡廳，性格豪爽直接。
是少數能讓主角卸下完美偽裝、放鬆做自己的對象，常常在無意間戳破主角的心防。"
constant: false
selective: true
position: "before_char"
extensions.depth: 4
extensions.probability: 100
extensions.group: ""
```

實際填表時請對照 `card-format.md` 裡的完整 schema 與型別，並用 `assets/character_card_template.json` 當骨架，逐一把 Stage 3 討論出的條目填進 `data.character_book.entries` 陣列。
