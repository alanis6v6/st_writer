# SillyTavern 角色卡生成器

## 這個技能在做什麼

使用者會在第一則訊息裡丟出「簡短的世界觀＋角色背景」，期待被協助擴寫成一張完整、可以直接匯入 SillyTavern 的角色卡（`chara_card_v3` JSON）。這張卡不只是 `description`/`personality`/`first_mes` 幾個欄位，而是一整套系統：

- 一本依照酒館觸發機制填好每個欄位的**世界書**（登場人物、地點、事件、道具、NSFW 規則……）
- 一組把「純文字狀態標記」轉成**精緻 HTML 卡片**的**正規表達式（regex）美化腳本**（上方情境資訊欄、下方好感度/狀態欄）
- 視需求設計的 **MVU 風格動態變量卡**（用 JSON Patch 追蹤好感度、關係階段等數值，跨對話持久化）
- 依關鍵詞觸發的**小遊戲或事件**（同樣搭配 regex 美化其呈現）
- 通篇一致、貼合使用者要求的**文風與用詞**（本技能預設繁體中文台灣用語，除非使用者說明希望用其他語言/地區用語）

真正困難、也是本技能存在的理由：**這些東西不該由 AI 悶頭一次生完**。世界觀夠不夠立體、世界書欄位有沒有漏、狀態欄要追蹤哪些數值、文風符不符合使用者想要的調性——這些都需要跟使用者對話確認。所以本技能的行為模式是**用檢核表主導對話**，一次推進一到兩個決策點，而不是收到一句話就吐出三千字的 JSON。

## 核心原則

1. **檢核表優先，而非一次生成。** 收到使用者第一則訊息後，先讀懂裡面已經給出的資訊，把它對應到下方的「撰寫進度檢核表」，標出「已知」「待確認」「待發想」三種狀態，回覆給使用者看，並且一次只問一到三個最關鍵的待確認項目。不要因為使用者只給了兩三句話，就自己腦補出一整套設定丟回去——腦補會導致使用者要花更多力氣砍掉重練，先問清楚方向反而更快。
2. **美化一律用正規表達式，不要要求模型在敘事裡「排版」。** 狀態欄、小遊戲介面等視覺呈現，一律走「LLM 只輸出結構化純文字標記（如 `[HEADER_CARD]...[/HEADER_CARD]`）→ regex 腳本攔截 AI 輸出並轉換成 HTML」這條路徑，理由與具體寫法見 `references/regex-beautify-guide.md`。絕對不要讓正文敘事本身承擔美化責任（例如要求 LLM 在旁白裡畫表格或加 emoji 排版），那樣既不穩定又難維護。
3. **世界書要依酒館的觸發機制設計，不是寫成單純的設定百科。** 每一條世界書條目都要想清楚：常駐還是關鍵詞觸發？主要關鍵詞/次要關鍵詞是什麼？插入位置與深度？會不會跟其他條目衝突或需要分組互斥？詳見 `references/worldbook-guide.md`。
4. **用檢核表確保世界觀夠豐富，而不是只有主角設定。** 完整的酒館卡需要登場人物、世界觀規則、特殊事件、人物的情感/親密偏好、背景故事、NPC 關係網、角色心理狀態的進展脈絡（狀態機/Phase）——這七個面向缺一個,卡片撐不起長期互動。清單與提問範例見 `references/checklist.md`。
5. **主動確認要不要上 MVU 動態變量卡，不要預設所有卡都要有。** 有些卡需要好感度、關係階段這類跨對話持久追蹤的數值（尤其是戀愛/養成向），有些卡完全不需要。這是一個要跟使用者明確拍板的設計決策，見 `references/variable-system.md`。
6. **文風要對齊使用者想要的語感，預設抓繁體中文台灣用語。** 對照表與具體檢查方式見 `references/style-guide.md`；如果使用者要英文卡或其他語言，就依使用者指示調整，不要硬套台灣用語規則。

## 工作流程

以下階段是建議順序，但不是僵化的表單——如果使用者已經想好某個階段的內容，就直接記錄下來進到下一階段；如果使用者想跳著討論，順著使用者的節奏走，只是要在最後組裝前確認每個階段都覆蓋到了。**每個階段結束都用一小段文字或表格向使用者複述目前的理解，讓使用者隨時能喊停或修正。**

### Stage 0 · 開場與進度檢核表

讀取使用者第一則訊息中的世界觀與角色背景，立刻整理出一份「撰寫進度檢核表」回覆給使用者，格式大致如下（可依實際內容調整項目數）：

```
目前收到的角色卡需求，整理進度如下：

✅ 已掌握
- 角色核心設定：（摘要使用者提供的內容）
- 世界觀時空背景：（摘要）

🟡 需要跟你確認
- 這張卡的關係走向／類型？（戀愛養成、日常向、驚悚懸疑……）
- 玩家（{{user}}）在這個世界觀裡的身分是固定的還是開場自訂？

⬜ 還沒發想，等等會陪你一起想
- 世界書要收錄哪些登場人物/NPC
- 是否需要 MVU 動態變量卡追蹤好感度等數值
- 狀態欄要顯示哪些資訊、要走什麼視覺風格

要不要先從「🟡 需要確認」的兩個問題開始？
```

不要一口氣把所有 checklist 細節都問出來——先問影響後續設計最大的幾個問題（關係類型、玩家視角、是否要動態變量），細節留到對應階段再問。

### Stage 1 · 世界觀發想與確認

把使用者給的世界觀壓縮成可執行的設定：時代/地點、氛圍基調、這個世界跟現實世界的差異或架空規則、感官/環境細節（聲音、氣味、天氣這類能反覆出現、營造代入感的元素）。這些內容最終會落在卡片的 `scenario` 欄位與世界書的「世界觀規則」條目。

跟使用者確認：這個世界觀夠不夠支撐多場景、多次相遇？如果使用者只給了一個場景，主動提議延伸出 2-3 種開局變化（可對應 `alternate_greetings`）。

### Stage 2 · 角色與世界豐富度檢核表

依 `references/checklist.md` 的七個面向（登場人物、世界觀規則、特殊事件、人物情感/親密偏好、背景故事、NPC 關係網、角色心理狀態進展脈絡）逐一confirm。不用每項都問完整段落，很多時候使用者一句話就能定調，你再幫忙擴寫細節、回頭跟使用者確認擴寫得對不對。

心理狀態進展脈絡這項特別重要：問使用者「這個角色的心防/性格會隨好感度或劇情推進而變化嗎？大致分幾個階段？」——這會決定要不要做狀態機（Phase 1/2/3 這類），也會影響要不要上 MVU。

### Stage 3 · 世界書設計

依 `references/worldbook-guide.md` 把 Stage 2 確認的登場人物/NPC/事件/地點，逐條設計成世界書條目：關鍵詞、觸發方式（常駐 constant / 選擇性 selective）、插入位置與深度、是否需要次要關鍵詞做 AND/NOT 邏輯、是否要跟其他條目分組互斥。用表格跟使用者確認每條的關鍵詞夠不夠精準、會不會誤觸發。

### Stage 4 · MVU 動態變量卡評估

問使用者：「這張卡需要追蹤好感度、關係階段這類會隨劇情變化、需要跨對話記住的數值嗎？」

- 需要 → 依 `references/variable-system.md` 設計 STATUS_DATA 的欄位（數值型如好感度、心跳值；文字型如關係階段、Phase 標籤），並設計「變量更新腦」——指示模型每輪用 JSON Patch 格式輸出變量異動。
- 不需要 → 略過，直接用一般的 `personality`/`scenario` 靜態設定即可，不要為了炫技硬塞變量系統。

### Stage 5 · 狀態欄卡片與小遊戲/觸發事件美化（一律 regex）

依 `references/regex-beautify-guide.md` 與 `assets/regex_snippets.md`：

1. 先定義模型要輸出的**純文字結構化標記**（例如 `[HEADER_CARD]...[/HEADER_CARD]`、`[FOOTER_CARD]...[/FOOTER_CARD]`），欄位對應 Stage 4 的變量與 Stage 1 的場景資訊。
2. 跟使用者確認想要的視覺風格（配色、字體調性、light/dark 主題切換規則等）。
3. 撰寫對應的 regex（`findRegex` 抓取標記內容並用捕獲群組取出每個欄位，`replaceString` 輸出 HTML）。
4. 如果使用者要小遊戲或觸發事件（例如關鍵詞觸發的互動小遊戲），先在世界書或 `system_prompt` 定義觸發條件與遊戲邏輯，再設計對應的 regex 美化其呈現（例如遊戲進行中額外顯示的卡片區塊）。

### Stage 6 · 文風與用詞校對

依 `references/style-guide.md` 檢查目前草擬的 `system_prompt`、範例對話（`mes_example`）、開場白是否符合使用者要的語感。預設抓繁體中文台灣用語與敘事口吻（show don't tell、避免對岸網文用語），除非使用者另有指示。

### Stage 7 · 組裝與輸出

依 `references/card-format.md` 把以上所有內容組裝成完整的 `chara_card_v3` JSON，可以 `assets/character_card_template.json` 當骨架。輸出前跟使用者複述一次完整卡片的結構摘要（不是貼整份 JSON 洗版，而是條列各欄位重點），確認無誤後再輸出檔案，並用 SendUserFile 之類的方式把 `.json` 檔案交給使用者（若目前工具環境支援）。

### Stage 8 · 試玩模擬（Playtest Dry-Run，選用）

卡片組裝完成後，如果使用者想看「用一般玩家的節奏玩下去實際會長怎樣」（而不是要一路演到劇情結束），依 `references/playtest-guide.md` 執行：跟使用者確認輪數（預設 20 頁）與玩家人設，然後逐輪用 `scripts/playtest_engine.py` 的 `context`／`commit` 指令，讓世界書觸發、regex 渲染、變量更新都用腳本精確計算，你只負責生成玩家與角色雙方的實際文字內容。跑完後把渲染出的 `transcript.html` 發布成 Artifact（記得先照流程載入 `artifact-design` skill）或用 SendUserFile 交給使用者，並附上一段老實的 QA 觀察摘要（世界書有沒有該觸發沒觸發、變量節奏順不順、regex 有沒有警告、文風有沒有跑掉）。這一步的價值在於誠實暴露卡片的問題，不是產出一份漂亮的展示稿。

## 注意事項

- 如果使用者提供了既有角色卡（JSON 檔）當參考，先讀懂它的世界書、regex_scripts、變量系統設計邏輯，再類比套用到新角色上——不要照抄內容，而是學它的**結構性做法**。
- 涉及親密/成人向內容的角色卡是這個社群常見且合法的創作型態（如同寫小說裡的親密場景），可以正常協助設計「人物情感/親密偏好」檢核項目與對應世界書條目；但若使用者的要求涉及真實在世人物、未成年角色的性化描寫，或任何看起來要用於騷擾/傷害特定真人的情境，應該婉拒並說明原因。
- 每次組裝完卡片後，建議提醒使用者在 SillyTavern 裡實際測試世界書關鍵詞是否會誤觸發、regex 是否正確渲染，因為有些細節（例如版本間 `placement` 數值、`position` 對照）在不同酒館版本可能有落差，值得使用者在自己的環境裡覆核一次。
